# Usability baseline — 2026-11-08

## Setup and reproduction

From the repository root run `bun run test:e2e -- e2e/usability-baseline.spec.ts --workers=1`. Playwright starts Vite and a fresh PocketBase in a temporary directory, removed when the server exits; it does not use `pb_data/` or `data/`. The script creates an invented D&D 5e game, character, 42 test spells, 42 test items, a 22-spell book, 15 live participants, and Satchel → Pouch → Token. Names include a per-run key. It logs viewport, document height/width, `window.scrollY`, focused element, and target top/height in CSS pixels. It also deletes its catalog fixtures and their references before the shared fixture removes the game. A failure trace is retained under ignored `test-results/`.

This exploratory script depends on the current interface and even waits for the current player-view loading behavior. Update or retire its assertions as the redesign changes those behaviors; do not treat them as desired UX regression checks.

Measurements below are one successful headless Chromium run at 1920×1080 desktop and Playwright's Pixel 8 emulation at 412×839, with no physical device or on-screen keyboard. Numbers can vary with fonts, timing and fixture-name wrapping. Some movement occurs because Playwright scrolls controls into view before clicking; this is identified below and is not proof of an unsolicited jump. This baseline describes the current working tree, including the owner's pre-existing catalog system-selection changes.

## Observed journeys

1. **Catalog load and shortening.** Open `/catalog` with D&D 5e selected; the script delays catalog responses by 600 ms. At scroll 0, the search top stayed at 492 desktop / 524 phone during load and after 30 results appeared; document height grew from 1080 to 3276 / 1043 to 3775. Search for the run's `Baseline … Spell`, focus remains in search, scroll to the bottom, and replace the text via keyboard with `Baseline … Spell 01`. Document height fell to 1080 / 1016 and scroll changed from 2196 → 0 / 2936 → 177; search retained focus and moved into view. This reproduces a jump **when typing while the search remains focused offscreen**; it does not establish the owner's exact sequence.
2. **Detail and return.** Open the single result; browser Back and the explicit “Back to catalog” both returned with an empty query and body focus. To test pagination and filters, search the same 42 spells, set Level 1, select Next, scroll to the last row, open it and use browser Back. Before opening, scroll was 756 / 1262; on return the immediate measurement was 0 / 278, query and Level were empty, and pagination showed page 1. Browser restoration can be asynchronous; these are sampled positions, not a promise of the final scroll in every run.
3. **Item and spell pickers.** In inventory choose “Add catalog item”, search the run's item prefix, scroll the inner results to the bottom, then search its `Item 01`. The results box was 360px high with `scrollTop` 2319 / 3057, then 55 / 73px with `scrollTop` 0. Selecting closes the picker and focus becomes body; the list reappears. Page scroll immediately after selection was 649 desktop / 1337 phone, but the click itself auto-scrolled to the result, so causation is not isolated. In the 22-spell book, “Add spell” → search `Spell 21` → select also closes the picker and leaves body focus; phone scroll was 70 at search measurement and 784 after selection, including Playwright's click scroll.
4. **Long book and nested inventory.** The 22 full descriptions produced a 7322px / 11381px document; the list began at y=454 / 755 at scroll 0. Inventory's item list began at y=913 / 1387 (below the phone fold). The visible name-sorted order was `↳ Baseline Pouch`, `↳ Baseline Token`, then other items and `E2E Satchel`; both nested depths had the same arrow and the parent appeared later. Container counts were visible but the list did not show the full parent path.
5. **15-person live combat.** Open `/games/<game>/encounters?encounter=<encounter>`. At scroll 0, the roster began at y=884 / 1364; the first expanded participant card was 268 / 486px high, roster height 4160 / 7423px, document height 6193 / 9392px. Scroll to the last participant (scroll 4370 / 8124), enter Current HP 6 and Conditions `Prone`, then Save: sampled scroll remained 4370 / 8124. “Add catalog creature” opens its picker **after** the long live roster: filtering the run's `Baseline … Creature` and selecting it added an entry while leaving the picker open. Clicking and locating that offscreen picker caused Playwright to scroll; the entry list was far below the initial viewport.
6. **Player live update.** Open `/games/<game>/encounter`, wait for subscription and scroll to bottom (868 / 1642). A separate API request changes the last participant's HP from 6 to 5; delay the player view's game read by 600 ms. During refresh the roster disappeared, document height became 1080 / 841, and scroll became 0 / 2. Once HP 5 appeared, desktop remained at 0; phone was back at 1642 in this run. The controlled delay makes the intermediate state visible; it is not a measurement of normal network latency.

## Interpretation and follow-up

- **Observed:** page shortening, lost catalog query/filter/page on back, and the player loading replacement can each disrupt context in the sequences above. Item/spell selection removes the focused picker; the creature picker behaves differently. The GM save tested did not move scroll.
- **Inferred from code, not independently isolated:** catalog results live in component state and are cleared during loading; `App.vue` keys the route view by path, and the detail link points to `/catalog`. Shorter documents can clamp browser scroll. `PlayerEncounterView.vue` sets its full loading state on realtime events; GM refresh rebuilds drafts but attempts to restore them. Initial loading, browser restoration timing, inline panels, focus/auto-scroll and unrelated live events are separate candidate causes. Do not attribute the owner's report to any one without their sequence.
- **Next steps:** use these journeys for step 4 search/history and step 6 picker regression checks; retest player updates/drafts in two real browser contexts for step 11. Check more viewport sizes, zoom, touch keyboard and actual devices in later steps. No performance conclusions follow from these small synthetic fixtures.
